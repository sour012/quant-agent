# 设计说明：五个关键取舍

这份文档记录「为什么这么做」，不是在重复 README。面试被追问细节时，看这里比看代码快。

## 1. 为什么用规则投票，而不用一个大模型打分

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| 让 LLM 直接输出「买/卖/持有」 | 表达力强、上手快 | 不可复现（同输入不同输出）、无法归因、回测无法审计、调用成本随回测天数线性上升 |
| 规则加权投票（本项目） | 完全确定、每一分可追溯、零调用成本、可单测 | 表达能力有限，规则要人工设计 |

结论：择时信号的**可信度来自可复现性**。一个说不清「为什么今天买」的信号，在回测里就算赚钱也不敢用。规则投票牺牲了表达力，换来了可审计——这正是回测要验证的前提。

多 Agent 的价值不在「更聪明」，而在**职责分离**：技术面看价格结构、情绪看市场心理、宏观看基本面传导，三者的错误模式不一样，合成后单类信号的失效不会立刻拖垮整体。

## 2. 为什么风险 Agent 不参与方向投票

风险 Agent 的分数天然 ≤ 0（波动越高只会降仓，不会看多）。如果把它放进加权平均，等于给综合分加了一个恒定的负偏置，结果是系统几乎不建仓——本项目第一版就是这样，877 个交易日只成交 2 次。

改成「方向层 3 个 Agent 投票 + 预算层风险 Agent 给上限」之后：

- 方向判断保持对称（有多有空）；
- 风险约束变成显式的乘数 `cap`，可以在报告里单独展示（"风险预算把仓位上限压到 70%"）；
- 调仓逻辑更清晰：方向决定「要不要买」，预算决定「最多买多少」。

工程启示：**当一个模块的输出天然是单边的，就不要把它当投票者，要当约束条件。**

## 3. 为什么必须做 T+1 和成本建模

T 日收盘后才有完整 K 线，因此信号只能用在 T+1。若用「T 日收盘价成交」，回测收益会系统性虚高——因为收盘价本身参与了信号计算。

成本同理：单边 8bp（佣金 3bp + 滑点 5bp）× 换手 43 倍 ≈ 2%~3% 的累计拖累，和本项目的超额亏损同量级。不建模成本的策略，在实盘会直接亏掉「回测里的那点 alpha」。

## 4. 为什么要自己写「防未来函数」的对齐逻辑

三个隐形的未来函数，都是数据对齐问题，不是代码 bug：

1. **海关数据发布滞后**：10 月的数据 11 月中旬才公布。如果按月份直接 join，10 月 1 日就能"看到"10 月全月出口额。本项目用「交易日往前推 25 天所在月份」作为当日已知的最新月份。
2. **收盘后新闻**：15:00 之后发布的快讯不能影响当日信号，统一顺延到下一自然日。
3. **滚动指标**：`rolling` 默认只看过去，但 `shift(-n)`、`pct_change(-n)` 这类写法很容易手滑。

对应的验证方式在 `tests/test_pipeline.py::test_no_lookahead_signal_matches_truncated_data`：把数据砍到当天再算一遍，信号必须完全一致。这比"我觉得没问题"可靠。

## 5. 为什么最后没有把收益做漂亮

技术模式默认「顺势」，但因子检验显示本区间动量 IC 为负（`ret20` 与未来 20 日收益的 Spearman 相关约 -0.03，`bias20` 约 -0.04）。也就是说 2023-2026 的沪深300 更偏均值回归，顺势系统在这里天然吃亏。

有两个选择：

- **A. 把参数调到这段历史最优**（把 sell_threshold、confirm_days 往过拟合方向拧）——回测会好看，但换一段历史就废，面试时只要问一句「你怎么验证这不是拟合」就崩。
- **B. 保留一套逻辑自洽的规则，如实报告跑输基准，并给出诊断和下一步**（本项目选择）。

选 B 的理由：这个项目的价值是**证明我能把研究流程做对**（因子检验 → 假设 → 实现 → 样本外验证 → 归因），而不是证明某个参数组合能赚钱。参数是最容易过拟合的东西，方法不是。

## 附：如果重做一次，我会改什么

1. 先做 `research/factor_ic.py`，再写技术 Agent —— 顺序反了，导致返工两次（趋势版 → 反转版 → 回踩版）。
2. 决策层一开始就把「方向」和「预算」分开，能省掉一轮结构性返工。
3. 数据层先固定「发布滞后」这类元信息（`publish_lag_days`），而不是事后补。
