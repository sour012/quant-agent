# 面试追问速查（对着代码回答）

> 用法：每条先给「一句话结论」，再给「代码位置」和「可以展开的细节」。
> 原则：不知道就说不知道，别编。这个项目最值钱的部分恰好是「发现了问题、量化了问题、说明了局限」。

## Q1 五个 Agent 怎么协作？会不会互相干扰？

**一句话**：串行流水线，每个 Agent 只读上游已产出的东西，写自己的 `Signal`，谁也不能回头改别人。

- 顺序：`collector → technical / sentiment / macro → risk → decision`（`src/qtagent/orchestrator.py` 的 `PIPELINE_ORDER`）
- 契约：`Signal(score, confidence, reasons, evidence)`（`src/qtagent/agents/base.py`）
- 边界：`ctx.peer_signals` 只追加不修改，所以下游能看到上游结论，上游看不到下游
- 为什么要分离：三类信号的失效模式不同（技术面怕震荡、情绪怕噪声、宏观怕滞后），合成后才不至于单点失效拖垮整体

## Q2 为什么不用大模型直接打分？

**一句话**：不可复现、不可归因、回测成本高。择时信号的可信度首先来自可复现。

- 规则投票：同输入同输出，877 个交易日可以逐日复盘（`fact_signal_daily.contributions` 存了每天的加权贡献）
- LLM 打分：同输入可能不同输出，回测无法审计，且无法回答"为什么今天买"
- 这个项目里 LLM 不是不能用，而是应该用在「新闻理解」（抽取事件与影响方向），而不是直接输出仓位

## Q3 怎么保证没有未来函数？

**一句话**：三个隐形泄漏点都做了处理，并且有单测把「砍掉未来数据」作为判据。

1. 海关发布滞后 → 用「交易日 −25 天所在月份」取最新可得月度值（`features.py::build_feature_frame`）
2. 收盘后新闻 → ≥15:00 的快讯顺延到下一自然日（`features.py::_daily_news_features`）
3. 滚动指标 → 只用 `rolling`/`shift(1)`，禁用负向 shift
4. 验证：`tests/test_pipeline.py::test_no_lookahead_signal_matches_truncated_data`，把行情砍到当天重算，信号必须逐位相同
5. 成交时序：T 日收盘出信号、T+1 开盘成交（`backtest/engine.py`）

## Q4 回测为什么跑输基准？

**一句话**：本区间动量因子是反向的，而默认技术模式是顺势的；这不是 bug，是假设和市场的错配。

- 累计收益 -5.22% vs 基准 -2.95%，最大回撤 -13.74% vs -24.09%，平均仓位 24%
- 证据：`research/factor_ic.py` 输出 `ret20` IC20 ≈ -0.03、`bias20` IC20 ≈ -0.04
- 成本：换手 43 倍 × 单边 8bp ≈ 2%~3% 拖累，与超额亏损同量级
- 我的结论：**方向判断没 alpha，风控有效**（回撤减半），下一版要做状态切换而不是调参

## Q5 参数是怎么定的？过拟合了吗？

**一句话**：样本内选参 + 样本外验证，仍然有过拟合风险，我在 README 里写明了。

- `scripts/sweep.py`：24 组网格，前 70% 选参、后 30% 验证，输出 `reports/sweep.csv`
- 观察到的现象：所有组合在样本外都是负收益，说明问题不在参数，在规则假设本身
- 没有做的事：没做 walk-forward（滚动窗口），这是明确的待办

## Q6 新闻情绪怎么算的？为什么回测里几乎不用？

**一句话**：词典法 + 时间衰减；免费源只能回溯约 10 天，所以回测里大部分时间走降级通道并显式标记。

- 打分：`src/qtagent/lexicon.py`，正负财经词典加权，`tanh` 压缩到 [-1,1]
- 聚合：半衰期 2 天的指数衰减，覆盖近 5 日（`_daily_news_features`）
- 降级：新闻不足时用「5 日动量 + 量比」代理，`evidence.degraded=True`
- 为什么不编历史新闻：那是伪造数据，回测结论会彻底不可信

## Q7 数据库为什么这么设计？

**一句话**：维度表 + 事实表；写入按主键先删后插，跨 SQLite/MySQL 都成立；多维检索用白名单映射避免拼 SQL。

- 表：`dim_agent` / `dim_region` / `fact_trade_monthly` / `fact_market_daily` / `fact_fx_daily` / `fact_news` / `fact_signal_daily`
- 幂等：`storage/db.py::upsert_df`，重复跑 ETL 不出脏数据
- 多维查询：`query_trade(start_month, end_month, flow, calibre)`，流向/口径通过 `_TRADE_FIELD_MAP` 白名单映射到列名
- 追溯：所有事实表带 `source` + `updated_at`；信号表存归因 JSON

## Q8 胜率只有 20%，这策略能用吗？

**一句话**：胜率低不等于亏钱，看盈亏比；但这套规则目前整体是负的，所以结论是「不能用」。

- 平均盈利 43,954 元 vs 平均亏损 13,601 元，盈亏比约 3.2:1
- 20% 胜率 × 3.2 盈亏比 ≈ 理论期望接近 0，实际被成本拖成负
- 趋势型策略的典型特征就是低胜率高盈亏比，问题在于本区间趋势太少

## Q9 要做实盘还差什么？

**一句话**：差执行层、差实时数据、差仓位对齐与风控熔断。

1. 实时行情与断线重连（当前是收盘后批量）
2. 订单管理：部分成交、撤单、涨跌停、T+1 卖出限制
3. 每日对账：`fact_signal_daily.target_position` 与实际持仓差异告警
4. 风控熔断：单日亏损阈值、连续回撤阈值、数据异常熔断
5. 监控：信号延迟、数据缺失率、Agent 弃权率
